# What are Terraform modules and what are the best practices for module reusability?

**Short answer:** Terraform modules are self-contained packages of configurations that encapsulate related resources into reusable building blocks, with best practices dictating explicit inputs/outputs, pinned semantic versioning, and minimal blast radius.

## Detail

Modules enable DRY (Don't Repeat Yourself) infrastructure and establish corporate golden paths.

### Best Practices for Enterprise Modules

1. **Avoid Monolithic Modules**: Do not create a single mega-module that creates a VPC, EKS cluster, RDS database, and Redis cache. Decompose into focused single-responsibility modules (`terraform-aws-vpc`, `terraform-aws-eks`).
2. **Explicit Inputs & Outputs**:
   - Provide clear `description`, `type`, and sensible `default` values for every variable.
   - Always output resource IDs and ARNs so downstream modules can consume them.
3. **Semantic Versioning in Module Registries**:
   - Reference modules via Git tags or private module registries, never raw unpinned branches:

     ```hcl
     module "vpc" {
       source  = "terraform-aws-modules/vpc/aws"
       version = "6.7.3" # exact pin; bump deliberately via PR (Renovate/Dependabot can propose it)
     }
     ```

4. **Never Hardcode Providers**: Root modules should configure provider credentials and versions; child modules should only declare `required_providers` without credentials.
5. **Test and document the contract**: `validation` blocks on inputs, `terraform test` against an `examples/` directory, and a README generated by `terraform-docs` so the documented interface cannot drift from the code.
6. **Treat breaking changes as majors**: removing an input, renaming a resource without a `moved` block, or anything that forces replacement is a major version bump with an upgrade note.

### The trade-off

Every module is an abstraction consumers must learn and trust. A module that merely wraps one resource and passes every argument through adds indirection without encoding any decision; a module with dozens of inputs becomes as complex as the resources it hides. Good internal modules are opinionated - encryption, logging, tagging, and naming on by default - and expose only what genuinely varies.

## Example

```hcl
# modules/s3-bucket/main.tf - an opinionated module: secure defaults, small interface
variable "name" {
  type        = string
  description = "Globally unique bucket name."
}

variable "tags" {
  type        = map(string)
  default     = {}
  description = "Extra tags merged onto the bucket."
}

resource "aws_s3_bucket" "this" {
  bucket = var.name
  tags   = merge(var.tags, { ManagedBy = "terraform" })
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket                  = aws_s3_bucket.this.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = "Enabled"
  }
}

output "arn" {
  value       = aws_s3_bucket.this.arn
  description = "Bucket ARN for IAM policies."
}
```

```hcl
# Root module: configure the provider, call the pinned module
module "exports" {
  source = "git::https://github.com/acme/tf-modules.git//s3-bucket?ref=v1.4.0"
  name   = "acme-prod-exports"
  tags   = { team = "payments" }
}
```

## Interview tips

- Start with "every configuration is a module; the directory you apply in is the root module", then describe child modules as the reusable unit.
- Name the anti-patterns: the kitchen-sink mega-module and the pass-through wrapper that encodes no decision.
- Pin module versions (registry `version` or Git `?ref=`) and describe upgrades as reviewed PRs where you read the plan for replacements.
- Explain why child modules declare `required_providers` but never configure providers: portability across accounts and regions, and aliases passed in via `providers = {}`.
- Likely follow-up: "how do you roll out a breaking module change to 40 consumers?" - a major version with `moved` blocks and an upgrade guide, adopted environment by environment.

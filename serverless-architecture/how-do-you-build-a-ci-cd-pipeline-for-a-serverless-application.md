# How do you build a CI/CD pipeline for a serverless application?

**Short answer:** Treat the whole application - functions, API definition, queues, tables, permissions - as **one versioned infrastructure artefact** deployed by a framework (AWS SAM, Serverless Framework, CDK, or Terraform), never by uploading a zip by hand. The pipeline builds and packages once, deploys to per-environment **separate accounts**, and promotes the same artefact upward. The serverless-specific parts are: **function versions plus aliases** as the deployment unit, **weighted alias traffic shifting** for canary releases with CloudWatch alarms that auto-roll-back, **short-lived OIDC credentials** instead of stored cloud keys, and testing that leans on real cloud resources in an ephemeral stack because local emulation only proves your code parses.

## Detail

### Package the application, not just the code

A serverless "deployment" includes the function code _and_ its triggers, IAM roles, environment configuration, queues, and API routes - they change together and must be versioned together. Use SAM or the Serverless Framework for function-centric applications, CDK when you want real programming-language composition, or Terraform when serverless sits inside a wider estate you already manage that way. What matters is that the deploy is declarative and repeatable: `sam deploy` or `terraform apply`, from CI, with the template in Git.

**Build once, promote the artefact.** Build the deployment package (and its dependency layers) once, upload it to an artefact bucket or ECR keyed by Git SHA, then have each environment deploy that same package with different parameters. Rebuilding per environment reintroduces the "you never tested what you shipped" problem, and with compiled dependencies (native Python wheels, Go binaries) it also invites architecture mismatches.

### Environments: separate accounts, not separate prefixes

Use a distinct AWS account (or subscription/project) per environment. Serverless makes this cheap - there is no idle capacity to pay for - and it gives you real isolation of quotas, throttling limits, and blast radius. Prefix-based separation inside one account means a runaway dev function can exhaust the account concurrency limit that production shares. Per-environment configuration comes from parameters and Parameter Store/Secrets Manager, not from branching in the template.

### Deploy safely: versions, aliases, and traffic shifting

This is the mechanism that makes serverless deployment genuinely safer than most:

- Publishing a **version** produces an immutable snapshot of code and configuration.
- An **alias** (`live`) points at a version, and event sources point at the alias.
- The alias can **split traffic by weight** between two versions, so a canary is a native platform feature rather than extra infrastructure.
- Bind the shift to **CloudWatch alarms**: SAM's `DeploymentPreference` (`Canary10Percent5Minutes`, `Linear10PercentEvery1Minute`) shifts traffic gradually and **automatically rolls back** if the alarms fire, with optional pre-traffic and post-traffic validation hooks.

That gives you canary deployment with automatic rollback in about eight lines of template - and it is the single best thing to describe in an interview, because it shows you know what the platform gives you for free.

### Testing strategy

- **Unit test the handler's logic** with the real event shape - generate it (`sam local generate-event`) or save a production event, because most bugs live in event parsing rather than business logic.
- **Integration test against real cloud resources** in an ephemeral per-branch stack. Local emulation (`sam local`, LocalStack) is useful for a fast loop, but it does not reproduce IAM, service quotas, event ordering, or eventual consistency - which is where serverless bugs actually are.
- **Ephemeral stacks per pull request**, torn down on merge. Serverless is the one architecture where this is genuinely cheap, so use it.
- **Contract-test the API** (OpenAPI validation) and smoke-test after every deployment against the alias.
- Keep an eye on cold-start impact of dependency growth - a bundle-size check in CI is a cheap guard.

### Security and permissions in the pipeline

- **Federate with OIDC** from GitHub Actions or GitLab into a per-environment deployment role. No long-lived access keys in CI, which is the most common real serverless security failure.
- **Least privilege for the deploy role**, and least privilege for each function's own execution role - one role per function, generated by the framework, not one shared `LambdaFullAccess` role. This is where serverless most often regresses, because it is easier to reuse a permissive role.
- Scan dependencies (SCA) and the template (`cfn-lint`, Checkov, `tfsec`) in CI, and generate an SBOM for the deployment package. See [how do you scan Infrastructure as Code before it is applied](../devsecops/how-do-you-scan-infrastructure-as-code-before-it-is-applied.md).

### The operational details that make it work

Deploy in dependency order (tables and queues before the functions that need them - the framework handles this if you keep them in one stack), remember that a stack update replacing a resource can be destructive (renaming a DynamoDB table deletes it), and version your API separately from your functions so clients are not broken by an internal refactor. Watch the deployment with the metrics that matter afterwards - errors, throttles, duration, DLQ depth - and let the alarms drive the rollback rather than a human watching a dashboard. See [how do you monitor and debug a serverless application](./how-do-you-monitor-and-debug-a-serverless-application.md).

## Example

```yaml
# template.yaml - canary deployment with automatic rollback, natively
Transform: AWS::Serverless-2016-10-31
Globals:
  Function:
    Runtime: python3.12
    Timeout: 20
    Tracing: Active
    AutoPublishAlias: live # every deploy publishes a version + moves the alias
    DeploymentPreference:
      Type: Canary10Percent5Minutes # 10% for 5 min, then 100%
      Alarms: # if these fire, CodeDeploy rolls back automatically
        - !Ref ErrorRateAlarm
        - !Ref P99LatencyAlarm
      Hooks:
        PreTraffic: !Ref SmokeTestFunction # validate before any real traffic
        PostTraffic: !Ref IntegrationTestFunction

Resources:
  CreateOrder:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: ./build/create-order # built once in CI, referenced by digest/SHA
      Handler: app.handler
      Environment:
        Variables: { TABLE: !Ref Orders, LOG_LEVEL: !Ref LogLevel }
      Policies: # per-function least privilege, not a shared role
        - DynamoDBCrudPolicy: { TableName: !Ref Orders }
      Events:
        Api: { Type: HttpApi, Properties: { Path: /orders, Method: POST } }
```

```yaml
# .github/workflows/deploy.yml - OIDC, build once, promote the same artefact
permissions: { id-token: write, contents: read } # OIDC: no stored cloud keys

jobs:
  build:
    steps:
      - uses: actions/checkout@v4
      - run: sam build --use-container # reproducible native deps
      - run: |
          sam package --s3-bucket "$ARTEFACTS" --s3-prefix "${{ github.sha }}" \
            --output-template-file packaged.yaml
      - uses: actions/upload-artifact@v4
        with: { name: packaged, path: packaged.yaml }

  deploy:
    needs: build
    strategy: { max-parallel: 1, matrix: { env: [dev, staging, prod] } }
    environment: ${{ matrix.env }} # prod gates on an approval
    steps:
      - uses: actions/download-artifact@v4
        with: { name: packaged }
      - uses: aws-actions/configure-aws-credentials@v4
        with: # a separate ACCOUNT and role per environment
          role-to-assume: arn:aws:iam::${{ vars.ACCOUNT_ID }}:role/deploy-serverless
          aws-region: eu-west-1
      - run: |
          sam deploy --template-file packaged.yaml --stack-name orders-${{ matrix.env }} \
            --capabilities CAPABILITY_IAM --no-fail-on-empty-changeset \
            --parameter-overrides LogLevel=${{ vars.LOG_LEVEL }}
      - run: ./scripts/smoke.sh "https://${{ vars.API_HOST }}/orders" # against the alias
```

## Interview tips

- Say first that the deployment unit is the whole stack - functions, triggers, IAM, tables - not a zip file. "We upload the zip from a laptop" is the practice this question exists to weed out.
- Function **versions plus a weighted alias with alarm-driven automatic rollback** is the highest-value thing to describe. Name `Canary10Percent5Minutes` or the equivalent; it shows you know canary is a native capability here.
- Insist on separate accounts per environment and give the serverless-specific reason: concurrency and throttling limits are account-wide, so shared accounts share blast radius.
- Mention OIDC federation instead of stored keys. It is the most common real security gap in serverless pipelines.
- Be precise about testing: local emulation is a fast loop, not a substitute, because IAM, quotas, ordering, and eventual consistency only exist in the cloud. Ephemeral per-pull-request stacks are cheap here and you should say so.
- Bring up per-function execution roles as the least-privilege discipline that serverless makes easy and teams still skip.
- Note the destructive-update trap - renaming a stateful resource can delete it - and that stateful resources often belong in a separate, slower-changing stack.
- Close on what you watch after deploy: errors, throttles, duration, DLQ depth, and alarms wired to the rollback rather than a person on a dashboard. See [what are serverless best practices](./what-are-serverless-best-practices.md).

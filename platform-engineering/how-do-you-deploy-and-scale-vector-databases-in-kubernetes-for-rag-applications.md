# How do you deploy and scale Vector Databases in Kubernetes for RAG applications?

**Short answer:** Deploy and scale vector databases (such as Milvus, Qdrant, Weaviate, or pgvector) on Kubernetes by decoupling query/indexing microservices, provisioning high-IOPS persistent storage (e.g. AWS `io2` / local NVMe), building HNSW index partitions in RAM, and implementing read-replica scaling for low-latency similarity search in Retrieval-Augmented Generation (RAG) pipelines.

## Detail

Vector databases store high-dimensional embeddings generated by AI models to enable fast similarity search (K-Nearest Neighbors / ANN). Operating them at scale in production requires specialized platform architecture:

### 1. Vector Database Architectures

- **Milvus:** Distributed cloud-native vector database architecture separating compute (QueryNodes, IndexNodes, DataNodes) from storage (S3/MinIO for vector logs, etcd for metadata).
- **Qdrant:** Rust-based vector database supporting native HNSW indexing, payload filtering, and distributed horizontal sharding.
- **pgvector (PostgreSQL):** Open-source extension adding vector similarity search capabilities directly to PostgreSQL instances, ideal for unified relational and vector data workloads.

### 2. High-Performance Indexing: HNSW vs IVF

- **HNSW (Hierarchical Navigable Small World):** Graph-based index delivering sub-millisecond query latency. Requires loading the entire index into RAM, demanding high-memory Kubernetes worker nodes.
- **IVF (Inverted File Index):** Clustering-based index balancing memory footprint with search speed.

### 3. Production Storage & Memory Tuning

- **Disk IOPS & Bandwidth:** Provision High-IOPS SSD storage (`io2` or local NVMe drives) for write-ahead logs (WAL) and segment persistence.
- **Memory Requests:** Memory limits must account for both uncompressed vector data and in-memory index overhead to prevent OOMKilled crashes during index building.

## Example

Qdrant Distributed Cluster Deployment manifest with high-performance storage:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: qdrant-cluster
  namespace: ai-platform
spec:
  serviceName: qdrant-headless
  replicas: 3
  selector:
    matchLabels:
      app: qdrant
  template:
    metadata:
      labels:
        app: qdrant
    spec:
      containers:
        - name: qdrant
          image: qdrant/qdrant:v1.18.0
          env:
            - name: QDRANT__CLUSTER__ENABLED
              value: "true"
          ports:
            - containerPort: 6333
              name: http
            - containerPort: 6334
              name: grpc
          resources:
            requests:
              memory: "16Gi"
              cpu: "4"
            limits:
              memory: "32Gi"
              cpu: "8"
          volumeMounts:
            - mountPath: /qdrant/storage
              name: qdrant-storage
  volumeClaimTemplates:
    - metadata:
        name: qdrant-storage
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: "gp3-high-iops"
        resources:
          requests:
            storage: 250Gi
```

Vector Similarity Search query against Qdrant gRPC endpoint (Python):

```python
from qdrant_client import QdrantClient

client = QdrantClient(host="qdrant-cluster.ai-platform.svc", port=6333)

# Search top 5 nearest vector embeddings in RAG context
results = client.search(
    collection_name="enterprise_knowledge_base",
    query_vector=[0.023, -0.412, 0.891, ...], # 1536-dim embedding vector
    limit=5,
    query_filter={"must": [{"key": "department", "match": {"value": "engineering"}}]}
)

for res in results:
    print(f"Document ID: {res.id}, Score: {res.score}")
```

## Interview tips

- Explain **HNSW indexing memory requirements**: graph indexes must fit in RAM for fast search; calculating required RAM (`num_vectors * dimensions * 4 bytes * 1.2 overhead`) is key to preventing node OOMs.
- Differentiate **Milvus** (disaggregated cloud-native architecture for billion-scale vectors) from **pgvector** (lightweight extension for existing Postgres databases).
- Highlight **hybrid search**: combining dense vector embeddings (semantic search) with sparse keyword search (BM25) to maximize RAG retrieval accuracy.
